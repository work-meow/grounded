# База знаний

Личная RAG-система: загружаете документы или подключаете Google Drive, Notion,
Dropbox, OneDrive, Яндекс.Диск — задаёте вопросы — получаете ответы со ссылками
на конкретные страницы.

```
                        браузер
                           │
                    Next.js + shadcn/ui
                           │  JWT в HttpOnly cookie
                           ▼
                   FastAPI  ──────────────►  PostgreSQL
                      │                      users / sources / documents
                LangChain agent              chats / messages
                      │
             search_knowledge
             list_sources
             read_document
                      │
                      ▼
              Pathway  /v1/retrieve
        usearch KNN + tantivy BM25 → RRF
                      ▲
        ┌─────────────┴──────────────┐
       S3                    подключённые источники
  загруженные файлы     Drive · Notion · Dropbox
                        OneDrive · Яндекс.Диск
```

Два процесса, три внешних сервиса. Индексация живая на всех входах: файл,
попавший в S3, становится доступным для поиска сам, без перезапуска и без
очередей — на загруженном `.md` это занимает пару секунд; изменение в
подключённом источнике подхватывается на следующем опросе (по умолчанию раз в
10 минут) и переиндексируется само.

```
backend/    FastAPI, агент, PostgreSQL          собственный venv
indexer/    Pathway: коннекторы, парсинг,       собственный venv
            чанки, индекс
shared/     ключи, манифест, печать секретов    ставится в оба
frontend/   Next.js
```

## Почему так

**Статус индексации нигде не дублируется.** В PostgreSQL нет колонки `status` —
она читается прямо из Pathway (`/v1/inputs`) на каждый запрос списка файлов.
Двум источникам правды нечему разъезжаться. Если индексер лежит, список файлов
всё равно отдаётся.

Кэша нет и не будет: он позволил бы интерфейсу утверждать, что документ
найден, когда процесс, который ищет, с этим не согласен.

Платить за это, впрочем, почти не приходится — после того как выяснилось,
откуда бралась задержка. Pathway отвечает на запрос только когда поток данных
дошёл до него, а движется он не быстрее самого медленного входного коннектора,
который по умолчанию коммитит раз в 1500 мс. То есть ждал не список файлов —
ждал **любой** запрос, включая поиск. Замеры на боевой машине: `/v1/retrieve`
1.1–1.9 с, `/v1/inputs` ровно 1.48 с, и почти всё это — ожидание такта. После
перевода входных коннекторов на 100 мс те же вызовы занимают 0.09–0.10 с.
В ответе агента с двумя-тремя поисками это четыре секунды из пяти.

Цена — движок тикает в пятнадцать раз чаще: CPU простаивающего индексера вырос
с 2.5% до 7%, а лог персистентности — с 79 строк в минуту до 938, поэтому эта
строка теперь фильтруется.

**У всех коннекторов одна раскладка метаданных.** Google Drive отдаёт
`id`/`name`/`modifiedTime`, Notion — дерево блоков, Dropbox — свои пути. Каждый
коннектор заканчивается в `connectors/contract.py`, который переписывает это в
тот же ключ `users/<user>/sources/<source>/<document>/<file>`, что пишет API для
загруженных файлов. Поэтому изоляция, статус индексации и цитаты работают для
подключённых источников без единой правки ниже по стеку — а коннектор, который
пропустил бы этот шаг, проиндексировал бы документы, не видимые никому.

**Новый источник перезапускает индексер, и это не костыль.** Граф Pathway
фиксируется в момент сборки — добавить коннектор в работающий процесс нечем.
Поэтому API пишет список источников в бакет, индексер следит за его ETag и
выходит с кодом 75, когда тот меняется; `restart: unless-stopped` поднимает его
обратно. Замерено на боевой машине: от записи манифеста до перезапуска — до 30
секунд (интервал опроса), сам перезапуск — 6–7 секунд, всё это время поиск
недоступен. Эмбеддинги заново не оплачиваются: `DiskCache` ключует их по
содержимому чанка. Без этой строчки `with_cache=True` не даёт ничего — она
включает кэш UDF, а UDF пользуется им, только если сам попросил.

**Чужие учётные данные запечатаны.** Токен Notion или refresh token Dropbox
доходит до системы один раз и сразу шифруется Fernet — и в таблице `sources`,
и в манифесте в бакете. Ни один эндпоинт не отдаёт конфигурацию обратно, ни
одна строка лога не содержит её: тот, кто её ввёл, и так её знает, а прочитать
её обратно можно было бы только чтобы показать кому-то ещё. У Google Drive
секрета нет вовсе — пользователь делится папкой с сервисным аккаунтом, что даёт
доступ на чтение к одной папке и отзывается из интерфейса самого Drive.

**Изоляция пользователей — на точном равенстве, а не на совпадении строк.**
Ключ в S3 (`users/<user>/sources/<source>/<document>/<file>`) разбирается
индексером обратно в метаданные каждого чанка, и поиск фильтруется выражением
`user_id == \`<uuid>\``. Обратные кавычки, не обычные: Pathway переписывает
выражение перед отправкой в движок, и одинарная кавычка доезжает до парсера
экранированной. В фильтр подставляются объекты `UUID`, а не строки — именно
типизация здесь и есть защита от инъекции.

**Гибридный поиск, а не только векторный.** BM25 находит точные термины —
фамилии, номера, ссылки на статьи — которые эмбеддинги регулярно теряют.
`HybridIndexFactory` объединяет обе выдачи через reciprocal rank fusion.

**Парсинг — по одной библиотеке на формат, а не универсальный комбайн.**
Формат определяется по сигнатуре файла, потому что Pathway отдаёт парсеру байты
без имени. `unstructured` и Docling были измерены и отвергнуты: оба тянут torch
ради PDF (~2 ГБ на образ) даже там, где нужен только текстовый слой, а
`unstructured` тратил 7.6 с на DOCX, который `python-docx` читает за 34 мс.
Итог — `pypdfium2`, `python-docx`, `python-pptx`, `openpyxl`: ~14 МБ, страницы
для цитат и никакого OCR, которого нам не заказывали.

**Два virtualenv, а не один.** `pathway[xpack-llm]` пинит `langchain<0.4` ради
адаптеров, которыми мы не пользуемся, и это несовместимо с `langchain>=1.0`,
нужным агенту. Процессы общаются по HTTP, поэтому ни одному не нужно дерево
зависимостей другого. `shared/` подключён к обоим как path-зависимость — не
через uv workspace, потому что workspace сводится к одному lock-файлу и одному
окружению, то есть ровно к тому, чего эти два проекта разделить не могут.

## Что нужно

- Python 3.13 — ставится самим `uv`, отдельно ничего готовить не нужно
- Node.js 22 (минимум 20.9)
- PostgreSQL 14+
- S3-совместимое хранилище (AWS, Cloudflare R2, Backblaze, MinIO)
- Ключ [OpenRouter](https://openrouter.ai) — и для модели агента, и для эмбеддингов

## Установка

```bash
# 1. база
createdb rag
psql rag -c "CREATE ROLE rag LOGIN PASSWORD 'rag'; GRANT ALL ON DATABASE rag TO rag;"

# 2. конфигурация — три файла, у каждого есть шаблон рядом
cp backend/.env.example         backend/.env
cp indexer/.env.example         indexer/.env
cp frontend/.env.example        frontend/.env.local

# секрет для подписи токенов
openssl rand -hex 32   # → JWT_SECRET в backend/.env

# ключ, которым запечатываются чужие учётные данные
uv run --project backend python -c \
  "from rag_shared.crypto import generate_key; print(generate_key())"
```

Заполните в обоих `.env` одинаковые доступы к S3 и `OPENROUTER_API_KEY`.
`SECRETS_KEY` тоже должен совпадать: API им запечатывает, индексер открывает.
Оставите пустым — подключение источников будет отключено, загрузка файлов
продолжит работать.

```bash
# 3. зависимости
cd backend         && uv sync && uv run alembic upgrade head
cd indexer         && uv sync
cd frontend        && npm install
```

## Запуск

Три процесса, каждый в своём терминале:

```bash
# индексер — поднимать первым, он проверяет ключ эмбеддингов на старте
cd indexer && uv run python -m rag_indexer.pipeline

# API
cd backend && uv run uvicorn app.main:app --reload --port 8000

# интерфейс
cd frontend && npm run dev
```

Выпустите себе токен и войдите с ним на <http://localhost:3000>:

```bash
cd backend && uv run rag-token --email вы@example.com
```

> При работе по обычному `http` на не-localhost хосте поставьте
> `COOKIE_SECURE=false` в `backend/.env`, иначе браузер отклонит cookie.

## Подключение источников

Пошаговые инструкции есть в самом интерфейсе, под каждым источником. Здесь —
то, что к интерфейсу не относится: настройка сервера для Google Drive, и
объяснение, почему у трёх сервисов процедура длиннее, чем хотелось бы.

**Notion и Яндекс.Диск** выдают долгоживущий токен, который достаточно один раз
скопировать. У Notion это Internal Integration Secret; у Яндекса — OAuth-токен,
и здесь легко ошибиться: страница приложения показывает ClientID и Client
secret, а нужен **не они**, а токен, который выдаётся после перехода по
`https://oauth.yandex.ru/authorize?response_type=token&client_id=ВАШ_CLIENTID`.

**Dropbox и OneDrive** выдают access token на час, поэтому им нужен refresh
token — а он выдаётся ровно один раз, при первой авторизации в браузере, и
только если попросить об этом явно (`token_access_type=offline` у Dropbox,
`offline_access` у Microsoft). Отсюда четыре поля вместо одного. Полноценный
OAuth-редирект избавил бы от ручного обмена кода на токен, но потребовал бы
регистрации приложения и коллбэка на нашей стороне — при личной установке это
дороже, чем один раз выполнить `curl`.

Google Drive устроен иначе: доступ даёт не пользователь через OAuth, а
развёртывание через сервисный аккаунт. Это меньше прав — аккаунт видит ровно ту
папку, которой с ним поделились, только на чтение, и доступ отзывается из
самого Drive, — но требует один раз настроить:

1. [console.cloud.google.com](https://console.cloud.google.com) → создайте
   проект;
2. APIs & Services → Library → включите **Google Drive API**;
3. Credentials → Create credentials → **Service account**;
4. у созданного аккаунта: Keys → Add key → JSON → скачайте файл;
5. содержимое файла **одной строкой** → `GDRIVE_CREDENTIALS_JSON` (индексер),
   адрес аккаунта (`...@....iam.gserviceaccount.com`) →
   `GDRIVE_SERVICE_ACCOUNT_EMAIL` (API, показывается в интерфейсе).

Дальше пользователь открывает нужную папку в Drive, даёт этому адресу право
«Читатель» и вставляет ID папки — часть ссылки после `/folders/`.

Подключение источника перезаписывает манифест в бакете, индексер это замечает
в течение 30 секунд и перезапускается за 6–7 секунд — всё это время поиск
недоступен. Уже посчитанные эмбеддинги не оплачиваются заново.

## Проверки

```bash
cd backend && uv run pytest && uv run ruff check .
cd frontend && npx tsc --noEmit && npx eslint . && npm run build
```

```bash
cd indexer && uv run pytest && uv run ruff check .
```

Тесты бьют по тому, что ломается незаметно, а не по тому, что легко проверить:

- **Изоляция пользователей.** Реальное JMESPath-выражение проверяется на
  метаданных, собранных реальным post-processor'ом, — и предварительно
  прогоняется через то же переписывание, которое делает Pathway. Ровно на этом
  шаге тесты однажды промахнулись: выражение было валидным JMESPath и невалидным
  для движка, а падал при этом весь процесс индексера.
- **Поток ответа.** Закрытая вкладка не бросает `Exception`, поэтому отдельно
  проверяется, что уже полученные токены сохраняются, а текст исключения не
  уезжает в браузер.
- **Парсеры.** Каждый формат собирается и читается обратно, так что обновление
  библиотеки не превратится в тихо пустые чанки. Zip-бомба отвергается.
- **Цитаты.** Нумерация не должна разъезжаться между тем, что видит модель, и
  тем, что показано в интерфейсе.
- **Коннекторы.** Каждый ходит в живой сервис, поэтому проверяется наша
  половина: раскладка метаданных (документ с неправильным ключом не виден
  владельцу и при этом нигде не ошибка) и дифф опроса — неизменившийся файл не
  переэмбеддится, изменившийся переиндексируется, удалённый уходит из индекса,
  а лежащий сервис не выглядит как «все файлы удалены». Отдельно один прогон
  через настоящий граф Pathway: именно на этой границе ошибка формы дала бы
  документы, принадлежащие никому.
- **Печать секретов.** Манифест проверяется на отсутствие открытых учётных
  данных, а битая запись в нём — на то, что она стоит одного источника, а не
  всего индекса.

## Деплой

Образы собираются в GitHub Actions и публикуются в GHCR. На сервере — только
`pull`: в `docker-compose.yml` нет секции `build`, поэтому `up` не может
случайно начать сборку.

Это не стилистический выбор. Первая попытка собрать три образа прямо на хосте
(2 vCPU, 4 ГБ, там же чужой прод) выбрала всю память и уронила машину.

На сервере нужны ровно два файла: `docker-compose.yml` и заполненный `.env`.
Репозиторий приватный, поэтому `curl` по raw-ссылке вернёт 404 — копируйте из
своей рабочей копии:

```bash
ssh root@СЕРВЕР 'mkdir -p /opt/rag'
scp docker-compose.yml .env.example root@СЕРВЕР:/opt/rag/

ssh root@СЕРВЕР
cd /opt/rag && mv .env.example .env
chmod 600 .env        # в нём ключи — заполнить и закрыть от чужих глаз

docker compose pull && docker compose up -d
```

`docker-compose.yml` придётся скопировать заново, если он изменился в
репозитории: `pull` обновляет образы, но не файл, который их описывает.

Обновление после сборки в CI — `docker compose pull && docker compose up -d`:
`pull_policy: always` и отсутствие секции `build` означают, что развернётся
ровно тот образ, который прошёл тесты.

PostgreSQL в compose нет намеренно: на хосте он уже есть, а второй экземпляр
только отнимал бы память. `DATABASE_URL` указывает на существующий.

Логи ограничены на уровне драйвера — 10 МБ × 3 файла на сервис. Pathway пишет
о каждом опросе S3 примерно дважды в секунду, и без этого потолка журнал
съел бы диск за недели. Потолок стоит у всех пяти сервисов, а не только у него.

Traefik отдаёт `/api` и `/` с одного хоста — поэтому cookie сессии
first-party, а CORS не участвует вовсе. У бакета свой хост: presigned-ссылки
открывает браузер, и подпись покрывает имя хоста, поэтому ссылка, подписанная
для внутреннего адреса, в браузере бы не прошла.

## Как добавить

**Инструмент агенту** — функция с `@tool` в `_build_tools`
(`backend/app/agent.py`). Она автоматически замкнётся на текущего пользователя.

**Коннектор к сервису, который умеет только «список и скачать»** — класс с
методами `list`/`fetch`/`close` в `indexer/rag_indexer/connectors/`, строка в
`Kind` и `REQUIRED_FIELDS` (`shared/rag_shared/connectors.py`), запись в
`_POLLED` и оформление в `frontend/app/(app)/sources/connected.tsx`. Опрос,
диффы, удаления, пропуск нечитаемого и переживание сбоев — общие. Ориентир:
Notion — 190 строк, Яндекс.Диск — 85.

**Коннектор, для которого у Pathway есть свой** — как `connectors/gdrive.py`:
взять таблицу у `pw.io.*` и пропустить через `conform`. `DocumentStore`
принимает список таблиц, так что новый вход добавляется рядом, а не вместо.

**Формат файла** — функция в `indexer/rag_indexer/parsers.py` и расширение в
`SUFFIXES` (`shared/rag_shared/formats.py`). Список один на всех: то, что
бэкенд принял, а индексер не читает, вечно висело бы в статусе «индексация».

**Поле в БД** — правьте `app/models.py`, затем
`uv run alembic revision --autogenerate -m "..."`.

## Ограничения

Осознанные упрощения помечены в коде комментарием `ponytail:` — там же назван
потолок и путь наверх.

- **Сканированные PDF не читаются.** `pypdfium2` достаёт встроенный текстовый
  слой; у скана его нет. OCR — это либо torch с layout-моделями (~2 ГБ на
  образ), либо внешний сервис. Путь наверх описан в `indexer/pyproject.toml`
  меткой `ponytail:`.
- **Агент компилируется на каждый запрос**, чтобы инструменты замыкались на
  пользователе. Против одного вызова LLM это ничего не стоит.
- **История чата отдаётся модели целиком** (последние 20 сообщений), без
  суммаризации. При длинных диалогах стоит подключить `SummarizationMiddleware`.
- **Один документ индексируется не более чем на 8 млн символов** (~4000 страниц).
  Индекс живёт в памяти индексера, а каждые 500 токенов — это отдельный вызов
  эмбеддингов. Без потолка файл на 64 МБ (наш же лимит загрузки) уводил индексер
  с 225 МБ до 1.7 ГБ, клал поиск на всё время обработки и ставил в очередь
  порядка ста тысяч платных запросов. Остаток файла просто не попадает в индекс,
  в логах об этом есть предупреждение.
- **Токен нельзя отозвать досрочно.** Проверка подписи не ходит в базу, поэтому
  выпущенный JWT действует до своего `exp`, даже если пользователя удалили.
  Для личной установки это осознанный размен; отзыв — это либо короткий TTL с
  refresh, либо список отозванных в базе, то есть поход в БД на каждый запрос.
- **О сломавшемся источнике никто не сообщает.** Если токен отозвали на той
  стороне, коннектор пишет ошибку в лог и оставляет последний снимок: документы
  остаются в поиске, но перестают обновляться, а интерфейс показывает источник
  здоровым. Так сделано намеренно — обратное означало бы, что любой сбой сети
  выметает документы из индекса, — но узнать об этом можно только из логов.
  Чтобы это исправить, индексеру нужен канал обратно в API, которого нет.
- **Один и тот же источник можно подключить дважды.** Получится два набора
  одинаковых документов и удвоенная плата за эмбеддинги. Это видно в списке
  (у документов будут разные имена источников) и чинится удалением лишнего.
- **Список источников общий на весь деплой.** Манифест переписывается целиком
  при каждом изменении, поэтому два пользователя, подключающие источник в одну
  и ту же секунду, могут перезаписать друг друга; следующее изменение это
  чинит. Для личной установки это осознанный размен против блокировки.
- **Dropbox и OneDrive требуют вставить четыре поля**, включая refresh token,
  который выдаётся один раз при первой авторизации. Полноценный OAuth-редирект
  избавил бы от этого, но потребовал бы регистрации приложения и коллбэка на
  нашей стороне — при одном пользователе это дороже, чем один раз скопировать
  токен.
- **Смена модели эмбеддингов обнуляет индекс.** Другая модель — другое
  векторное пространство; всё придётся переэмбеддить. При $0.02 за миллион
  токенов это дёшево, но это не бесплатно и не мгновенно.
- **Pathway распространяется под BSL 1.1.** Для личного использования это не
  ограничение, но перед коммерческим запуском проверьте Additional Use Grant.
