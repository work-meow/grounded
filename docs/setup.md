# Настройка и деплой

Установка и запуск — в [README](../README.md#быстрый-старт). Здесь то, что в
него не поместилось: подключение источников, сервисный аккаунт Google и
развёртывание на сервере.

## Мелочи, о которые спотыкаются

При работе по обычному `http` на не-localhost хосте поставьте
`COOKIE_SECURE=false` в `backend/.env`, иначе браузер отклонит cookie сессии.

Индексер поднимайте первым: он проверяет ключ эмбеддингов на старте, и лучше
узнать о неверном ключе сразу, чем на первом вопросе.

## Подключение источников

Пошаговые инструкции есть в самом интерфейсе, под каждым источником. Здесь —
то, что к интерфейсу не относится.

**Notion и Яндекс.Диск** выдают долгоживущий токен, который достаточно один раз
скопировать. У Notion это Internal Integration Secret; у Яндекса — OAuth-токен,
и здесь легко ошибиться: страница приложения показывает ClientID и Client
secret, а нужны **не они**, а токен, который выдаётся после перехода по
`https://oauth.yandex.ru/authorize?response_type=token&client_id=ВАШ_CLIENTID`.

**Dropbox и OneDrive** выдают access token на час, поэтому им нужен refresh
token — а он выдаётся ровно один раз, при первой авторизации в браузере, и
только если попросить об этом явно (`token_access_type=offline` у Dropbox,
`offline_access` у Microsoft). Отсюда четыре поля вместо одного.

**S3-совместимое хранилище** — один коннектор на всех: свой MinIO, Backblaze
B2, Cloudflare R2, Wasabi, Selectel, VK Cloud, AWS. Нужны адрес, бакет, ключ и
секрет; регион и префикс — по желанию. Адрес проверяется на то, что не ведёт
внутрь частной сети (см. [design.md](design.md#адрес-который-называет-пользователь)).

### Google Drive: сервисный аккаунт

Доступ даёт не пользователь через OAuth, а развёртывание через сервисный
аккаунт. Это меньше прав — аккаунт видит ровно ту папку, которой с ним
поделились, только на чтение, и доступ отзывается из самого Drive, — но требует
один раз настроить:

1. [console.cloud.google.com](https://console.cloud.google.com) → создайте
   проект;
2. APIs & Services → Library → включите **Google Drive API**;
3. Credentials → Create credentials → **Service account**;
4. у созданного аккаунта: Keys → Add key → JSON → скачайте файл;
5. содержимое файла **одной строкой** → `GDRIVE_CREDENTIALS_JSON` (индексер),
   адрес аккаунта (`...@....iam.gserviceaccount.com`) →
   `GDRIVE_SERVICE_ACCOUNT_EMAIL` (API, показывается в интерфейсе).

Дальше пользователь открывает нужную папку в Drive, даёт этому адресу право
«Читатель» и вставляет ID папки — часть ссылки после `/folders/`.

### Что происходит после подключения

Подключение перезаписывает манифест в бакете, индексер замечает это в течение
30 секунд и перезапускается за 6–7 секунд — всё это время поиск недоступен.
Уже посчитанные эмбеддинги не оплачиваются заново.

Один и тот же источник нельзя подключить дважды: у каждого считается отпечаток
полей, задающих место (папка, токен, путь), и он уникален в пределах
пользователя. Иначе получились бы два набора одинаковых документов и удвоенная
плата за эмбеддинги. Отпечаток не спасает от повторного OAuth: другой refresh
token у той же папки Dropbox выглядит новым источником.

Обратно, из индексера в API, идёт второй документ в том же бакете —
`state/sources.json`. После каждого опроса индексер пишет туда, чем кончилась
попытка по каждому источнику, а список источников это показывает: «проверен
3 мин назад · 10 файлов» или причину отказа. Причина классифицируется на
стороне индексера в одну фразу и никогда не является текстом исключения — в нём
бывают внутренние адреса и сам токен. Отчёт старше нескольких интервалов
считается недействительным: он переписывается после каждого прохода, поэтому
«всё в порядке» трёхчасовой давности означает не «всё в порядке», а «никто не
смотрел».

## Деплой

Образы собираются в GitHub Actions и публикуются в GHCR. На сервере — только
`pull`: в `docker-compose.yml` нет секции `build`, поэтому `up` не может
случайно начать сборку.

Это не стилистический выбор. Первая попытка собрать три образа прямо на хосте
(2 vCPU, 4 ГБ, там же чужой прод) выбрала всю память и уронила машину.

На сервере нужны ровно два файла: `docker-compose.yml` и заполненный `.env`.

```bash
ssh root@СЕРВЕР 'mkdir -p /opt/rag'
scp docker-compose.yml .env.example root@СЕРВЕР:/opt/rag/

ssh root@СЕРВЕР
cd /opt/rag && mv .env.example .env
chmod 600 .env        # в нём ключи — заполнить и закрыть от чужих глаз

docker compose pull && docker compose up -d
```

Обновление после сборки в CI — `docker compose pull && docker compose up -d`:
`pull_policy: always` и отсутствие секции `build` означают, что развернётся
ровно тот образ, который прошёл тесты. Сам `docker-compose.yml` придётся
скопировать заново, если он изменился в репозитории: `pull` обновляет образы,
но не файл, который их описывает.

Несколько решений, которые стоит знать, прежде чем менять compose:

- **PostgreSQL в нём нет намеренно.** На хосте он уже есть, а второй экземпляр
  только отнимал бы память. `DATABASE_URL` указывает на существующий.
- **Логи ограничены на уровне драйвера** — 10 МБ × 3 файла на сервис. Pathway
  пишет о каждом опросе S3 примерно дважды в секунду, и без этого потолка
  журнал съел бы диск за недели. Потолок стоит у всех пяти сервисов.
- **Traefik отдаёт `/api` и `/` с одного хоста** — поэтому cookie сессии
  first-party, а CORS не участвует вовсе. У бакета свой хост: presigned-ссылки
  открывает браузер, а подпись покрывает имя хоста, поэтому ссылка,
  подписанная для внутреннего адреса, в браузере бы не прошла.
